CASE STUDIES

我處理過的工程問題

串接的難處多半不在把 API 接通，而在廠商的例外情況發生時，金流和資料還是對的。

「結果未明」不等於「失敗」：避免限流造成的重複入帳

情境
轉帳錢包把點數轉入遊戲商時，如果請求逾時，系統會呼叫查單 API 確認結果。查單回「失敗」，就把點數退還給會員。
問題
某平台的查單 API 和撈注單共用同一組請求次數限制。超過時廠商回傳限流錯誤碼，回應裡沒有資料欄位。原本的判斷是「沒有資料就是查無此單」，限流回應被當成失敗，系統就退點；但廠商其實已經入帳，會員在兩邊都有錢。
解法
只有在「API 回應成功，而且明確查無這筆單」時才判失敗；限流、逾時、格式異常一律標記為處理中，等下一輪重查。同時把狀態碼改成字串嚴格比對，因為 PHP 7 的鬆散比較會讓 'abc' == 0 成立，非數字的錯誤碼可能被誤判成成功。
學到的事
處理金流時，「確定失敗」和「不知道」要分開。不知道的時候寧可晚一點，也不要做出不可逆的退款。

查單回應會被判成什麼

成功API 成功，且查到這筆單 失敗 → 退點API 成功，且明確查無此單 處理中限流、逾時、格式異常，稍後重查

修正前

失敗 → 退點限流錯誤（沒有資料欄位），被當成查無此單
// 示意版本，非原始碼
if ($ok && isset($res->data) && count($res->data) === 1) {
    return SUCCESS;
}
if ($ok && isset($res->data) && empty($res->data)) {
    return FAIL;       // 確定查無此單
}
return PROCESSING;    // 結果未明，下一輪重查

撈注單時間窗的護欄：排程和手動補單都要守規則

情境
注單同步靠排程，依時間區間向遊戲商拉單。營運人員也可以在後台手動選一段時間補單。
問題
某平台規定查詢的結束時間必須早於現在 2 分鐘，太接近現在會直接回錯誤。排程有扣掉 120 秒，但剛好卡在邊界，網路延遲或伺服器時鐘差一點就會失敗；手動補單路徑則完全沒有這層限制，只要選到現在時間就會出錯。另一個平台也有類似規則（5 秒）。
解法
把緩衝抽成一個常數，140 秒 = 120 秒硬限制 + 20 秒網路與時鐘誤差。排程和手動補單都把結束時間往前修正到「現在 − 140 秒」，整段落在禁區就直接略過，不送出請求。
學到的事
外部 API 的限制要守在每一條呼叫路徑上，不能只顧排程。邊界值也要留緩衝，不要剛好壓線。

結束時間能落在哪裡

可查詢

const END_BUFFER_SEC = 140; // 120 硬限制 + 20 緩衝
